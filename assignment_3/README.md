## 1. Overview & Research Objectives

This study investigates shared-memory parallelism and data-level SIMD vectorisation applied to square dense matrix multiplication ($n \times n$), focusing on how thread count $p$ ($1 \le p \le 16$) governs performance on an asymmetric multi-core processor (Apple Silicon M2 with 4 Performance cores and 4 Efficiency cores).

The empirical investigation addresses four core research questions:
1. **Framework Overhead at $p=1$:** What is the exact execution overhead introduced by the OpenMP threading runtime when restricted to a single thread ($p=1$) relative to an equivalent pure sequential C baseline compiled without multi-threading runtime linking?
2. **Strong Scaling & Architectural Regimes:** How does speedup $S(p) = T_{\text{seq}}(n) / T_p(n)$ and parallel efficiency $E(p) = S(p) / p$ behave across homogeneous P-cores ($p \in [1, 4]$), heterogeneous P+E cores ($p \in [5, 8]$), and oversubscription ($p \in [9, 16]$)?
3. **Work Scheduling on Asymmetric Cores:** How does work distribution (`schedule(static)` vs `schedule(dynamic, chunk)`) influence parallel load balancing when cores have disparate clock speeds (3.50 GHz Avalanche vs 2.42 GHz Blizzard)?
4. **Vectorisation Extension (ARM NEON):** What is the isolated acceleration factor of 128-bit ARM NEON SIMD vectorisation (`fmla.2d`), and how does it interact with thread-level parallelism before saturating shared memory bandwidth?

## 3. Experimental Protocol & Reproducibility

Every measurement adheres strictly to the common experimental protocol established in the course specification:
1. **Controlled Inputs & PRNG:** Matrix operands $A$ and $B$ are initialized deterministically using the SplitMix64 64-bit linear generator (seed $S = 42$), ensuring bit-for-bit identical input operands across all executions, methods, and thread counts.
2. **Numeric Precision:** All floating-point operations use 64-bit IEEE 754 double precision (`double`).
3. **Strict Timing Boundaries:** Time is measured using monotonic clocks (`clock_gettime(CLOCK_MONOTONIC)`). The timer captures exclusively the arithmetic parallel loop; memory allocation, data generation, and checksum calculation are strictly excluded.
4. **Warm-up & Repetitions:** Each configuration executes 1 warm-up run (discarded) followed by 5 consecutive measured repetitions. Central tendencies are reported as **Medians** and dispersion is measured via the **Interquartile Range (IQR)**.
5. **Anti-DCE Protection:** A checksum $\sum_{i,j} C_{ij}$ is verified on every repetition to prevent Dead Code Elimination (DCE).
6. **Memory Profiling:** Process resident memory is documented via `getrusage(RUSAGE_SELF, ...)` reporting Peak Resident Set Size (Peak RSS).

## 4. Hardware & Benchmark Environment

All experiments were executed on an Apple Silicon testbed:
- **Processor:** Apple M2 (ARMv8.5-A architecture, 5 nm)
  - 4 Performance cores (*Avalanche*, up to 3.50 GHz, 128 KB L1D / 192 KB L1I per core, 16 MB shared L2 cache)
  - 4 Efficiency cores (*Blizzard*, up to 2.42 GHz, 64 KB L1D / 128 KB L1I per core, 4 MB shared L2 cache)
  - 8 physical cores, 8 logical processors (1 thread per core, SMT disabled)
- **Memory Subsystem:** 8.0 GB Unified Memory (LPDDR5-6400, 128-bit bus, 100 GB/s bandwidth)
- **Operating System:** macOS Darwin 25.6.0 (Kernel 26.6.2, arm64)
- **Compiler & Toolchain:**
  - Apple Clang 21.0.0 (`clang-2100.1.1.101`)
  - LLVM OpenMP runtime (`libomp` 23.1.5 via Homebrew)
  - Compilation flags: `-O3 -Wall -Wextra -std=c99 -Xclang -fopenmp -I/opt/homebrew/opt/libomp/include -L/opt/homebrew/opt/libomp/lib -lomp`
  - Typesetting: Typst v0.15.1+

## 5. Summary of Key Findings

1. **OpenMP Framework Overhead at $p=1$:** Running the parallel kernel with $p=1$ is **$2\times$ slower** than pure sequential C ($S(1) \approx 0.47 - 0.53$). This directly quantifies the runtime cost of OpenMP thread-pool structures, barrier overhead, and inhibited compiler register optimizations.
2. **Three Strong Scaling Regimes:**
   - *Regime I ($p \in [1, 4]$):* Pure P-cores deliver near-linear scaling, reaching $22.81\text{ GFLOPS}$ ($n=1024$).
   - *Regime II ($p \in [5, 8]$):* E-cores join execution; lower clocks (2.42 GHz) and narrower IPC yield diminishing marginal returns, peaking at $29.63\text{ GFLOPS}$ (Static).
   - *Regime III ($p \in [9, 16]$):* Oversubscribing 8 physical cores causes involuntary OS preemptive context switching; at $n=2048$, runtime regresses from $0.65\text{ s}$ ($p=8$) to $0.80\text{ s}$ ($p=16$) (an $18\%$ performance penalty).
3. **Dynamic Scheduling Solves Heterogeneity Bottleneck:** Static scheduling divides work into equal slices ($n/p$), forcing fast P-cores to idle at implicit barriers waiting for slow E-cores. Dynamic scheduling (`schedule(dynamic, 8)`) allows P-cores to consume $\approx 70\%$ of the matrix, boosting throughput by **$+11.7\%$** ($29.63 \to 33.09\text{ GFLOPS}$, $S = 2.51\times$).
4. **ARM NEON SIMD & The Memory Wall:** 128-bit NEON FMA instructions (`fmla.2d`) accelerate floating-point arithmetic. However, at $n=2048$ ($96\text{ MB}$ payload exceeding the $16\text{ MB}$ L2 cache), 8 active cores saturate the $100\text{ GB/s}$ memory bus, creating an insurmountable memory wall for single-node shared-memory scaling.

## 6. Quick Start & Reproduction

To reproduce all builds, correctness tests, benchmarks, plots, reports, and presentation packages:

```bash
cd assignment_3

# 1. Build the parallel C binary
make build

# 2. Run automated correctness and concurrency tests (119 configurations)
make test

# 3. Execute empirical benchmarks (generates CSV logs in benchmarks/results/)
make benchmark

# 4. Generate publication figures and Typst tables
make plots

# 5. Compile the formal 7-page research report
make report

# 6. Compile the 4-slide presentation and Spanish defense guide
make presentation

# 7. Build complete submission zip package
make package
```

Or execute everything end-to-end with a single command:
```bash
make all
```
